# Documentation RAG pipeline

Turns a folder of raw Markdown documentation into:
- a cleaned sections dataset
- an ontology
- two LoRA adapters (Qwen2.5)
- three RAG systems evaluated on synthetic questions

Everything runs from [`main.ipynb`](main.ipynb).

## Requirements

- Python 3.10 or newer
- An NVIDIA GPU is recommended. The pipeline was run on an RTX 3080 Ti (12 GB), where a full run takes about 20 minutes. It also works on CPU, much more slowly.
- About 6 GB of disk for the models, downloaded on first use: `Qwen/Qwen2.5-0.5B-Instruct`, `Qwen/Qwen2.5-Coder-0.5B-Instruct` and `BAAI/bge-m3`. None of them needs a Hugging Face login.
- The raw documentation folder (`docs_raw/`). It is not included in this repository.

## Running

1. Put the raw documentation somewhere on disk, laid out as `<docs_raw>/<project_name>/<version>/**/*.md`.
2. Tell the notebook where it is: edit `DOCS_RAW_DIR` in section 1 of `main.ipynb`, or set the environment variable:
   ```bash
   export DOCS_RAW_DIR=/path/to/docs_raw
   ```
3. Run the notebook:
   ```bash
   jupyter lab main.ipynb
   # or headless:
   jupyter nbconvert --to notebook --execute --inplace --ExecutePreprocessor.timeout=-1 main.ipynb
   ```

All outputs are written to `data/`. In notebooks or scripts, import `rag_etl` before `torch`: it sets environment variables that torch needs on machines without the Python development headers.

## 0. Pipeline Overview
The objective of the exersise is to create a small open weigthed model thata answers questions from the Documentation. 
This in summary is a RAG with a knowledge base grounded on the documents that are given. 
We will answer this as if we were delivering a PoC.
There are some aproaches for doing a RAG, the text implies that we should train a model for this task, the usual way for this is adding memory to a model so that it memorizes the relevant information from the documentation. This pipeline implements a fine-tuning approach using LoRA (Low-Rank Adaptation) adapters on the Qwen2.5 model family to specialize it for documentation question answering.
The big issue with this pipeline is that the model doesn't know how to answer questions, it only knows a little bit more about our documentation. So if we wanted to train a model in this fashion we would need to provide it with a large dataset of question-answer pairs derived from the documentation. 
The other way to implement a RAG is with with a retrieval-augmented generation approach, where the model uses a separate retrieval system to find relevant documents and then generates answers based on that retrieved context. 
And the final way is to use both aproaches, i.e. create a knowledge base and add memory to the model.
In this pipeline the objective is to create a base experiment to test wich one of the approaches works better for the given documentation dataset. 

To create a vector database there are some simple ones like just leting some of lanchaing tools create it automatically, but for this I will use another aproach that is getting the relationships and entities from the text before adding it to a graph database. For simplicity we will use a json with the taxonomy and langchains implementation of ChromaDB.
Given That I don't know the relationships and entities of the family of documents I will let Claude generate a base ontology and then train a model to get the relationships and entities from a given text. This will force the model to extract the trained relationships and entities from a given text. 

Now That the ontology is created we create the 3 different RAG systems and evaluate them in a dataset  questions generated, this questions 80 come from a synthetic dataset generated from the documentation itself, ensuring they are answerable by the knowledge base, while 20 unanswerable questions serve as a control group to test the system's ability to refuse irrelevant queries. All of this questions are generated by Claude.

In this section all the files are loaded and parsed. The files are splitted by either the #..n header or the html header <h..n> the text of each section is mapped to a dataframe that has the following columns: ["path", "file_name", "project_name", "version", "section", "text"]  
The next part of the etl is finding duplicates and choosing the rigth one for keeping, namely the latest version of the project. The method for finding duplicates is MinHash LSH (Locality Sensitive Hashing) with a threshold of 0.8, which effectively identifies near-duplicate sections based on their content fingerprints. This ensures that only unique sections are retained for training and evaluation, reducing redundancy in the dataset.
Also if the section is marked as "TO DO" then we also raise a flag in this cases.

### 4.2 Training data (`entity_instruct`, tokenization, split)

We are training the both the ontology extractor adapter and the memory adapter in almost the same fashion.
First we tokenize the data with a BPE tokenizer compatible with qwen 2.5. Namely we map the text that we extracted in the etl to this tokenizer. And in the same moment we  tokenize the relationships and entities that Claude generatd as a promt for the llm. Namely a text that has the structure:
      {
            "instruction": Extract the entities and relationships from the following document in the specified JSON format.",
            "input": "a string that contains the text, the section, the version, the document name and the project name" ,
            "output": entities generated by claude,
        }
and the Tokens generated are the X and the tokens generated shifted by one are the Y's

Finally we split the Xs and Ys in train (80%), test (10%), dev (10%) datasets. The objective of the test set is to create an early stoping (or early weigth saving) and the dev set is to get the train result on a dataset that never was involved in training. Namely in the following pipelines we will save the model that had the lowest error on the dev set, even if the descent function keeps going down in the train dataset.

## Next steps

<!-- TODO: what you would do next and why. -->

* As this is a PoC the objective was to show that the best way to deploy such RAG is using extended memory, and that memorizing the codebase probably isn't as usefull and adds time to deploy. Nevertheless the results show that an hybrid method is probably the best one in terms of not answering unknown questions. 
* The next steps should be, improve the ontology by cleaning some entities that are generic, and checking one by one so that the entities and relationships make sense in MeLi. So that the retriever improves. 
* We should change the cosine similarity as the evaluation method in 5.4, and use some bigger llm to decide wether the answer is good or not. Or use cross encoders trained with the task of deciding if someting is similar, independent or opposing. 
* If we wanted to deploy this, ChromaDB should disapear and be replaced for something like Neo4j AuraDB or some sort of graph  database that MeLi has licence and  has integrations with lang chain. 
* Depending on the scope, time, and machine budget  we should also try different models, probably some bigger ones, or more recent ones to see if the quality of the answers improve.
* When the model is deployed a continious feedback loop with the users is important to understand wether the ontology is accurate and relevant.
